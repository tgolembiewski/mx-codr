Everything the mx-codr harness does

An AI agent builds the Mendix app with mxcli. The harness gives it one short rule file it reads on every turn, eight skills it reads when a part of the app calls for one, and a starter kit for its Playwright tests. Nothing runs while the agent builds: no gate, no hooks, no verdict.

1What it is

25lines in the always-on rule file
8skills installed beside mxcli's
4files in the starter test kit
0hooks, gates or settings edits
  • The source is mxcodr/ in this repository: install.sh, the installer overlay/install.mjs, the rule file and the kit in overlay/templates/, the skills in overlay/skills/.
  • The agent proves its own work with tests it keeps in tests/; whether a run built what was asked is measured from outside, by harness-eval/.
  • v1 (the gate tests/gate.sh, hooks, checkers and the rulebook) was removed on 2026-11-01 and is kept in the tags v1-best-hb1 and v1-last.

2The rule file

overlay/templates/mxcodr.md, installed word for word for Claude Code; Cursor gets the same text under its own frontmatter, Codex, opencode and Pi get it as a block in AGENTS.md with their skills folder named instead.

 1# Keep your checks as tests
 2
 3Every check you make of the running app — a browser flow per role, a refusal, data isolation, a
 4computed value, an API call — goes into `tests/` as a re-runnable automated test (Playwright for the
 5browser), never a throwaway script. Each requirement of the request gets a test that asserts its actual
 6content (the value, the order, the refusal, both sides of a rule), not only that a page opens. Before you
 7say you are done, run the whole suite once and show it passing.
 8
 9Write them as plain `@playwright/test` specs on top of `tests/mx.ts` (sign-in and sign-out, dialogs, grids, OQL, forged calls; take `test` and `expect` from `./mx`), with your own helpers beside it, and sign out at the end
10of each test (the trial runtime allows six sessions). Prove a refusal by attempting the forbidden action
11as that role (a call, a URL, an API request) and asserting that the server refuses it, plus the allowed
12side as the permitted role; never add a button, widen access or lower security so a test can see a message.
13Write and run the tests yourself in the foreground, never through a background agent, and never end your turn while a test run or an agent is still going. **You are done only
14when** you have printed a table `requirement -> test that asserts it` covering every requirement of the
15request (write the missing tests first), then run the whole suite once as `npx playwright test --shuffle`
16in `tests/` and shown it green with `sessions left: 0`. Never edit `tests/mx.ts` or `tests/mx.teardown.ts`
17to silence a check; fix the leaking test. Stop the app with
18`./mxcli run stop`, and any other process only by the exact PID you started, never by a name pattern
19(`pkill`, `killall`): that also kills the person's own browsers and test runs.
20
21Before building a part, read its project skill in `.claude/skills/` (beside mxcli's): `durable-tests`
22what deserves a test; `app-security` sign-in, roles, row isolation; `spacing-and-layout` menu, Back,
23signed-in user, icons, spacing; `naming-and-captions` variables, captions, widgets `<Page>_<What><Type>`;
24`module-structure` modules and folders; `files-and-images` uploads. Read each of these skills whole, one file per read, never through `head`, `cut` or a combined `cat`; of mxcli's own skills in `.ai-context/skills/` read only the section you need.
25Marketplace widgets only from publisher Mendix or Mendix Labs.
  • Lines 1-7: keep every check as a re-runnable test, one per requirement that asserts its content, and show the whole suite passing. Byte for byte the rule of run sk2 (overlay/templates/keep-tests.md); the installer refuses a written file whose first 7 body lines differ.
  • Lines 9-12: write specs on tests/mx.ts (taking test and expect from it), sign out after each test (six trial sessions), prove a refusal by attempting the forbidden action, never weaken the app so a test can see a message.
  • Lines 13-19: run the suite in the foreground; done only after a printed table requirement -> test that asserts it covering the whole request (missing tests written first) and one npx playwright test --shuffle run shown green with sessions left: 0; never edit the kit to silence a check; stop the app with ./mxcli run stop and other processes only by their own PID.
  • Lines 21-25: which skill to read before which part of the app, and Marketplace widgets only from Mendix or Mendix Labs.

Every written rule file is checked: first byte #, no frontmatter (the .mdc: only Cursor's own), no body line equal to ---.

3The skills

Installed beside mxcli's own skills, in each chosen agent's skills folder; the list is overlay/lib/skills.mjs. The agent reads a skill when the rule file or the skill's description sends it there.

skillwhat it coversreference files
durable-testsWhat deserves a test and how to keep it: plain Playwright specs on the kit, one worker, a flow per role, both sides of every rule, the whole suite shuffled at the end.reference/mendix-dom.md
app-securityProduction security with strict mode, roles with Administration.User, a demo user per role, row isolation, refusals proven by attempting the action as the wrong role.

4The starter test kit

overlay/templates/tests/, copied into the app's tests/ only when a file is absent; from then on it is the app's own and no later install overwrites it.

filewhat it is
tests/mx.tsThe helpers below, each commented with the Mendix fact it relies on; no app names.
tests/mx.teardown.tsRuns after the whole suite: prints sessions left: N and fails the run on a leak, naming the users.
tests/playwright.config.tsOne worker, baseURL from APP_URL, the teardown. Left out when the app has a Playwright config at its root.
tests/package.json@playwright/test pinned to 1.64.1 (it has --shuffle). Left out when the app has a package.json or Playwright config at its root; the installer prints the pin instead.

Beside the kit, tests/film.mjs (from overlay/templates/film.mjs) is written on every install, also when the kit is the app's own: it films a test when a person asks (the film-tests skill). The app's config is never edited, so a normal run records nothing; the film lands in .mxcli/films/.

5The installer

cd <folder> && bash mxcodr/install.sh [--db hsqldb|postgres] [--agent claude[,cursor,codex,opencode,pi]] [--remove-agent <name>] [--theme <name>] [--yes] [--boot] [--request <file>] [--no-app]

The folder is the current one (or the one holding mxcodr/ when run from inside it), or named first: bash mxcodr/install.sh <app folder> .... With no .mpr there the installer first creates the app with mxcli new in a temporary folder and moves it in, keeping every file already there (MX_VERSION, default 11.12.1; APP_NAME, default the folder name in letters and digits; on Windows a Studio Pro of that version must be installed); --no-app stops instead. Node 20 or later; on Windows, Git Bash.

  1. mxcli 0.29.0: the recorded one, PATH, or the app's ./mxcli, else a download into .mxcodr/bin/; ./mxcli is made that binary when it is a shim, a dead link or a binary that does not run here.
  2. Database: --db, else the last install's, else postgres when port 5432 answers, else hsqldb.
  3. Agents: on a terminal without --agent (and without --yes) the installer asks which coding agent(s) will work in the app: 1 Claude Code, 2 Cursor, 3 Codex, 4 opencode, 5 Pi, several as 1,5, Enter = the last install's, else Claude Code. --agent adds to the last install's agents; an agent's rule and skills go only when it is deselected or named with --remove-agent. No terminal or --yes: the last install's (else Claude Code) and a note naming them and how to add another. The summary has one start line per agent.
  4. The app's look: --theme one of atlas, navy, teal, amber, plum, forest, else the last install's (its frame refreshed), else asked once on a terminal (Enter = atlas, Mendix's own look). No terminal or --yes: nothing applied, the app keeps mxcli new's look. Only theme/ files change; node .mxcodr/theme.mjs <name> changes it later.
  5. Caches: mxcli setup mxbuild, mxcli run --local --setup, then mxcli init --sync-skills ..
  6. Upgrade cleanup: the v2 gate (./mxgate, .mxgate/) and v1's files (tools/mdl-checks/, tests/gate.sh, its rule files, plugins and only our hook and permission entries) go; the app's tests, docs/requests/ and docs/brain/ stay.
  7. Rule file, skills, test kit, tests/film.mjs as above, then .mxcodr/theme.mjs with the themes and .mxcodr/installed.json (bundle, mxcli, db, agents, skills, the kit files written, theme, requests).
  8. --request <file>: the request saved word for word as docs/requests/NN.md. --boot: one smoke boot, then stopped.

6Changing the harness

  • Edit mxcodr/overlay/, raise BUNDLE in overlay/lib/mx.mjs.
  • node --test 'mxcodr/test/*.test.mjs': rule format, skills free of gate words, install placement per agent, the test kit, the themes, and survival of mxcli init (with mxcli 0.29.0 on PATH).
  • Measure with harness-eval/bin/run.sh <prompt> <label>; the score is a line in harness-eval/results/results.jsonl.
