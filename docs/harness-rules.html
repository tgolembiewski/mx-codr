Everything the mx-codr harness does

An AI agent builds the Mendix app; the harness makes it prove the work is finished. One command, bash tests/gate.sh, answers with one of three verdicts, and only one of them means done.

DONE — every check passed NOT DONE — failed: <checks> NOT DONE — could not run: <checks>

1What it is

mx-codr sits on top of mxcli, the command line for a Mendix model. It turns that into a delivery workflow for five agents: Claude Code, Codex, Cursor, OpenCode and Pi, on macOS, Linux and Windows.

  • Tests first. For each feature the agent writes a failing browser test, then builds until it passes.
  • One definition of done. The gate runs the tests, Mendix's own consistency check and every rule below.
  • No broken model. Every MDL script is tried on a copy of the model first; a script that would break the build never touches the real .mpr.
  • A proper Mendix app. One menu, icons, one layout, Back buttons, a URL on every page, Users and My account, no leftover MyFirstModule.
  • A readable, secure model. Business captions, process folders, reuse, Atlas spacing, and Mendix's security best practices.
  • Nothing to operate. The person runs the installer once; skills, rules and hooks make the agent use everything else on its own.

2How a feature gets built

The loop the skills teach and the hooks enforce.

  1. AskThe person asks for a feature.
  2. TestThe agent writes tests/verify-<feature>.test.sh.
  3. RedThe test fails: the feature is not there yet.
  4. BuildAn MDL script, checked on a copy, then applied.
  5. GreenThe test passes (--only says PASSED).
  6. GateEleven verdicts; only the full run says DONE.

3The installer

mxcodr/install.sh on macOS and Linux, bootstrap.ps1 on Windows. It checks what the machine has, installs what is missing, and lists plainly what it could not do.

The project

  • Creates a Mendix app with mxcli new when the folder has none, and picks the Studio Pro version (it asks on a Mac with several).
  • Offers Atlas or one of five themes (navy, teal, amber, plum, forest); bash tests/theme.sh switches later.
  • Asks how the app runs: locally (runtime and PostgreSQL on the machine, changes live in about a second) or in Docker.

The tools

  • mxcli: the one release the harness is tested with (MXCLI_TESTED, v0.25.0), checksum-verified.
  • Node, playwright-cli and its browser, MxBuild for mx check, PostgreSQL; Docker only in Docker mode.
  • On Windows: Git for Windows, the junctions and the ARM64 fixes Studio Pro's mxbuild needs and, for Mendix 11.15, Studio Pro's own Gradle 9.5.1, JDK 25 and rspack bundler.
  • What needs a person (a JDK, starting a Docker daemon) is listed with the command to run.

The harness files

  • Skills, rules, hooks, plugins, lint rules and checkers, each where each of the five agents looks.
  • The gate and its parts in tests/; the checkers in tools/mdl-checks/.
  • A syntax digest generated from the project's own mxcli.

Existing apps

  • Writes a baseline of the paths that can be tested: paths that existed before the install warn, new ones block. Captions and widget names get their baseline at the first DONE.
  • Installs the rulebook in tests/rulebook/ and keeps each card's ## Local section word for word. It keeps tests/harness.env, and moves old level switches from it into the cards.
  • Ignores test artefacts and credential files in git.

4What the agent reads

Kept small on purpose: a session reads one skill up front, and every other file is named by the finding that needs it.

Always in context

  • Project rules (.claude/rules/, .cursor/rules/, Pi's system prompt): how users sign in, Production security and strict mode from the first script, how the gate works, which files are the person's, ask before any git command that writes.
  • Syntax digest: the topic indexes of ./mxcli syntax and the pitfalls that cost sessions the most time.
  • A reminder on every prompt, added by a hook.

5Hooks

They fire on their own. Claude Code and Codex get shell hooks, Cursor its own adapters, OpenCode and Pi a plugin that calls the same core.

On every prompt

remind-skills
  • Adds the project rules as context and marks the session, so the database snapshot and the stop hook know which session is running.

Before mxcli exec

before-mxcli-exec → tests/precheck.sh
  • Applies the script to a scratch copy and runs mx check there. A script that fails, or one that would add build errors, is refused; the real model is untouched.
SCRIPT01
The same document is created in two scripts: whichever runs last wins. The hint offers alter only for the kinds mxcli can alter.
STALE01
Re-running an old script would undo later changes to its pages and flows.
TEST01
A new page or ACT_ microflow that no test names yet: the test comes first.

After mxcli exec

after-mxcli-exec
  • Says whether a restart is needed and shows the coverage gaps.
  • Records which script was applied, so STALE01 can compare later.

When the agent wants to stop

stop-gate (Codex, Cursor)
  • Runs the gate and sends the agent back to work unless it ends in DONE.

On every tool call

guard-harness-env
  • The session may not change what judges it: no editing harness files or tests/harness.env, no gate switch set inline, no rewriting a baseline.

Part A · mx-codr's own rules

Before a script changes the app

The agent changes the app with MDL scripts. Before a script runs for real, mx-codr tries it on a copy. If a rule below fails, the real app is not touched.

RuleWhat it checks, in plain wordsLevel
precheckThe script is run on a copy of the app first. If it stops halfway, or if Studio Pro would show new errors afterwards, it is refused. The app is never left half-changed.Blocks
SCRIPT01Each page, microflow, entity or constant is created in only one script in mdlsource/. If two scripts both create the same page, running the older one again silently throws away the newer version. One-off repair scripts kept elsewhere are not compared.Blocks
STALE01An old script cannot be run again if that would undo changes made to its pages or microflows later. Moving a document to another folder does not count as a change.Blocks
TEST01Test first: before a new page or a new ACT_ microflow is added, a browser test for it must already exist. Fixing something that is already in the app is fine.Blocks

The browser tests

Tests are scripts in tests/ named verify-<feature>.test.sh. Each one opens the running app in a browser, clicks through a feature like a user would, and checks the result.

RuleWhat it checks, in plain wordsLevel
TESTS01Every browser test passes. Microflow unit tests (*.test.mdl) are not run by the gate; it shows the command that runs them.Blocks
COVERAGE01Every page and every ACT_ microflow has a test. A test says which pages and microflows it tests in a comment at its top, # covers: Order_List, ACT_Order_Save. This rule checks that every page and ACT_ microflow appears in such a comment, and that every name in those comments really exists in the app (a renamed page leaves an old name behind).Blocks
RUNTIME01While the tests ran, the Mendix server logged no errors. A test can pass while something failed in the background.Warning
VIS01On the page a test ends on, no two widgets lie on top of each other.Warning
VIS02The page does not scroll sideways.Warning
VIS03No text is cut off because its box is too small.Warning
VIS04A chart fits on one screen, in height and in width.Warning
LOOK01Only when switched on: an AI model has looked at a screenshot of every page.Warning
LOOK02Only when switched on: none of those screenshots was judged to look wrong.Warning
WAIT01Points out a test that pauses for a fixed time, or waits for something that may never come. It pays that time on every run.Warning

Every path through the app has a test

mx-codr reads the app and lists everything a user can run into: messages, workflow decisions, data only some users may see. Each of these needs a test. Paths that already existed when mx-codr was installed only warn; new ones block (WF01 always blocks).

RuleWhat it checks, in plain wordsLevel
OUTCOME01Every message the app can show (a success message, a validation error, a "credit limit exceeded" refusal) is checked by a test: the test makes the message appear and reads it on the screen.Blocks
WF01A microflow that approves or rejects a workflow task first checks that the person clicking is someone the task was assigned to. Without that check, anyone allowed to run the microflow can decide someone else's task.Blocks
WF02Every outcome of every workflow task (approve, reject…) is chosen in a test, and the test logs in as both people: the one who starts the workflow and the one who decides.Blocks
ISO01When a role may only see its own records (for example a customer sees only their own orders), a test logs in as that role and checks that their own records are there and someone else's are not.Blocks
ROLE01Every demo user's role is used by at least one test.Blocks
SVC01Every published REST or OData service is called by a test.Blocks

Readable microflows

A colleague should understand a microflow by reading its captions, without opening every activity.

RuleWhat it checks, in plain wordsLevel
CAPTION01Every activity (retrieve, create, change, commit, delete, show page, call…) has a caption in business words, like "Find the customer's open invoices".After DONE
CAPTION02No activity keeps the caption Mendix gives it by default, like "Retrieve Invoice" or "Commit object".After DONE
CAPTION03Every decision has a caption.After DONE
CAPTION04A decision's caption is a question and ends with "?", like "Is the order approved?".After DONE
CAPTION05A decision's caption is not the expression itself ($Order/Total > 1000). It says the question in words.After DONE
CAPTION06Every loop has an annotation saying what it walks through.After DONE
CAPTION07A loop has no caption: mxcli drops loop captions, so the text belongs in the annotation.Blocks
CAPTION08Points out a decision whose caption was overwritten by its expression.Warning
VAR01No variables named like $Int1, $tmp or $x. A name says what the variable holds, like $OpenInvoiceCount.Blocks
VAR02No variable names ending in _List, _Object or _Obj: $OverdueInvoices, not $Invoice_List.Blocks
REFRESH01When the Save button of a pop-up commits an object and closes the pop-up, the commit refreshes the client. Otherwise the list behind the pop-up does not show the new or changed row until the user reloads.Blocks
DS01A data grid, list view or gallery whose data source is a microflow that only retrieves rows uses a Database source instead. The database then pages, sorts and filters, which is much faster.Blocks
EVENT01An entity's after-commit event microflow does not commit its own object again with events. That commit starts the same event again: an endless loop.Blocks
EVENT02A before-commit event microflow that can say "no" (return false) is set to raise an error. Otherwise the save is skipped and the user gets no message at all.Blocks
EVENT03Points out a commit "without events" on an entity whose event microflow sets or checks something: that work is silently skipped.Warning
EVENT04Points out a plain Save button on an entity whose before-commit event can refuse: the user sees only "An error has occurred". Save through a microflow with a validation message instead.Warning
ERR01Points out an error handler that nobody would notice: it should log, show a message, raise the error again or return.Warning
PERF02Points out a loop over database rows that only adds them up or counts them. The database can do that in one query.Warning
PERF03Points out a database call for every row inside such a loop (a retrieve, a Java action, a sub-microflow that reads data): with 10,000 rows, 10,000 calls.Warning
PERF05Points out a retrieve of a whole table followed by an if that keeps some rows. Filter in the retrieve's XPath instead.Warning
PERF06Points out a loop that only looks for the highest or lowest value. One sorted retrieve of the first row does it.Warning
PERF07Points out a search on attributes that no index covers. The finding prints the index to add.Warning
PERF08Points out an index that no search in the app uses. It only slows down saving.Warning

Based on Mendix's own security best practices. Every finding of the last run is in .mxcli/security.txt.

RuleWhat it checks, in plain wordsLevel
PRODUCTION01App security is set to Production. At Prototype level Mendix ignores the XPath constraints on access rules, so a test can pass on an app that shows everyone's data.Blocks
STRICT01Strict mode is on. Without it, a clever user can read and change data through the browser in ways the pages never offer.Blocks

WRITE01Points out a role that may change fields only the system should set, like a total or a status. The finding names the fields to remove and the associations to keep.Warning
EXTENDS01Points out an entity that extends the user account (System.User or Administration.Account). Keep business data in its own entity, linked to the account.Warning

7Reading the verdict

  • DONE (exit 0): every step passed. --only and --tests-only say PASSED, never DONE.
  • NOT DONE — failed (exit 1): each failing step prints its findings, the fix, and the tests/checks/<step>.md file to read.
  • NOT DONE — could not run (exit 2): a check or the app could not run; the line says why.
  • Warnings are listed apart and never block: fix them with the next fix, not in a gate run of their own.
  • Timing per step and a closing list of what still blocks DONE.

8The person's settings

A rule's level and its exceptions are lines in the ## Local section of its card in tests/rulebook/: level: block, warn, info or off, and except: Module.Document. The rest is in tests/harness.env. The guard refuses a session that edits either, or sets a switch inline.

SettingEffect
level: off in PRODUCTION01Skips the Production requirement, for an app with no users.
level: block or off in VIS01–04, RUNTIME01, CAPTION01–06, SCOPE01, NAME01–02Makes those warnings block, or turns them off.
level: block in a paths cardOld paths without a test block too.
except: in a paths cardA path deliberately left without a test.
except: in UNUSED01A document kept on purpose though nothing uses it.
level: off in TEST01Turns off test-first in precheck.
level: warn or block in LINT01Shows mxcli lint's advice under the warnings, or makes lint errors block.
level: block in WAIT01The coverage step fails on tests that wait for time.
MDL_DB_RESET=sessionDatabase snapshot per session, restored after the first DONE.
MDL_VISUAL_REVIEW=agentA model that reads images judges each page's screenshot.

The switches that set these levels in tests/harness.env until bundle 2026.10.10.2 (MDL_VISUAL, MDL_CAPTIONS, MDL_KEEP_UNUSED ...) are no longer read; the installer moves them into the cards.
