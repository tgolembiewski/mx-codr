How the harness is wired

Read left to right: a person installs once, the files land in the app, the agent reads one rule file on every turn and a skill when a part of the app calls for one, and keeps its checks as tests. One thing is wired into the agent's tools, in Claude Code (since bundle 2026.11.18.2) and, in the Studio Pro extension, Codex (since 2026.11.18.6): the skill gate, two hooks that refuse a model change or a test file until the agent has read the project skill for it whole (for Codex: in its own command, nothing cut from the output it saw). No command is wrapped, no verdict is printed into its context.

1 · The person

cd <folder>
bash mxcodr/install.sh

Once per app; again to upgrade or repair.

2 · The installer

overlay/install.mjs

Pins mxcli 0.32.0, applies the chosen look (theme/ only), caches MxBuild and the runtime, removes earlier bundles' files, writes ours, then syncs mxcli's skills.

3 · Files in the app

rule file (with the brain rule and the app-docs update sentence) · skills (app-docs with its template and fingerprint) · tests/mx.ts … · tests/film.mjs · docs/brain/ (mxcli brain init when missing) · .mxcodr/ (coverage on: tests/coverage.mjs)

Plain files the agent's own host loads; for Claude Code also .mxcodr/skill-gate.mjs and its two hooks in .claude/settings.local.json.

4 · The agent

./mxcli exec · ./mxcli run · npx playwright test

Builds with mxcli, boots the app, runs its suite, shows it passing.

5 · Measured outside

harness-eval/bin/run.sh · score.py · check_<prompt>.py

An independent check the agent never sees, after the run.

What reaches the agent's context

Every turn

The 38-line rule file: first which project skill to read whole before which part (before the plan and before ./mxcli syntax), then keep checks as tests, prove refusals by attempt, finish only after a requirement-to-test table (coverage on: after node tests/coverage.mjs shows 0 missing) and one green shuffled run with no session left, stop processes by PID, and never change a Marketplace module.

On demand

A skill's SKILL.md when the rule file or its description sends the agent there, and its reference/ files when the skill points to them. The kit's tests/mx.ts when the agent writes a spec.

On a refusal (Claude Code; Codex in the extension)

The skill gate's reason, when a model change (./mxcodr-live exec, mxcli exec, mxcli -c) or a tests/**/*.spec.ts write (Codex: by apply_patch) needs a project skill not read whole yet in the session: the SKILL.md paths to read (Codex: in .agents/skills/, one per command with max_output_tokens: 30000 and the // @exec line, line ranges after a cut). Nothing else is injected: no gate verdict, no wrapped mxcli. What the agent sees from mxcli is mxcli's own output.

Kept by the installer

--request <file> saves the request word for word as docs/requests/NN.md; the agent reads it like any file.

Live mode: the same harness inside Studio Pro

The Studio Pro extension (spikes/studio-pro-ext/) carries this bundle in its payload and installs it from its pane with live: true: the same files, with the edits of overlay/lib/live.mjs and a second rule file .claude/rules/mxcodr-live.md, plus .claude/rules/mxcodr-plan.md while the pane's "Plan first for bigger requests" is on (live.33, from templates/plan-first.md), and since bundle 2026.11.18.3 the same rule for Codex, Pi and Copilot in AGENTS.md between <!-- mxcodr-plan:start --> and <!-- mxcodr-plan:end --> (from templates/plan-first-agents.md, only when the app has an AGENTS.md; an AGENTS.md with nothing else of the person's still counts as generated); since bundle 2026.11.18.5 that rule has the agent wrap its plan in <!-- mxcodr:plan --> / <!-- mxcodr:plan-end -->, which the extension's bridges turn into the pane's plan card. Codex's own rules in the extension's Codex home follow the app's permission preset: under Trust (approval policy never) running the app and the tests is allowed, under Ask and Standard Codex asks (spikes/studio-pro-ext/README.md, "Codex: Plan first and Trust"). File mode is unchanged.

The project brain (since bundle 2026.11.14.1): the rule text ends on the brain rule (overlay/templates/brain.md), the same in file and live mode. One switch in the agent's environment decides who approves: the extension sets MXCODR_PANEL=1 for every agent it starts, and then the person approves captures in the panel's end-of-turn card, a plan's Requirement: lines (each anchored, since bundle 2026.11.18.7, at the new page or microflow that will build it) are captured and promoted on Approve, and the panel's session-start brain pack replaces reading docs/brain/. Without it (an agent started from a terminal) the agent promotes only what the person approved in the chat and keeps mxcli's own brain reading.

How a run is measured

  • AGENT=claude MODEL=claude-sonnet-5-5 bash harness-eval/bin/run.sh <prompt> <label>: mxcli new, then install.sh <app> --db hsqldb --agent <agent> --request prompt.txt, then the agent unattended.
  • After the agent ends, the app is restarted with ./mxcli run stop and ./mxcli run --local and score.py adds one line to harness-eval/results/results.jsonl: time, tokens, turns, scope, test files, and the checks of check_<prompt>.py.
  • The run's transcript and logs stay in harness-eval/results/runs/; a written report goes to docs/sessions/<date>-<name>/.
